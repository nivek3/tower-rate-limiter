# PostgreSQL：过期时间取整与 fillfactor 对照实验

日期：2026-11-01（Asia/Shanghai）。基线是当前未提交迁移，已经包含上一轮的锁定读取/RETURNING 优化，未把这次收益与更早版本混算。

## 结论

过期时间向上取整到秒，明确增加 HOT 更新并降低 WAL 和物理空间增长；效果随同一个 key 的重复更新频率变化。
fillfactor=80 单独使用不能突破过期索引变化带来的 HOT 限制；与取整组合后有额外收益，但吞吐未在所有负载下稳定提升。
建议优先把取整作为落地候选。fillfactor=80 相比仅取整额外减少约 3%～9% WAL，但增加约 25% 的初始 heap 空间，不作为本次必须改动的默认值。
**本轮仅保存试验 SQL，未修改正式迁移或现有数据库。**

共完成 **36 轮、2,449,152 次测量调用，失败事务为 0**；每轮实际更新数与调用数完全一致。所有版本均通过取整边界、精确 burst、拒绝不改 TAT/expiry、key 隔离及 64 并发恰好放行 8 次的预检查。

## 方法与控制条件

- 独立 PostgreSQL 17.10 容器，1 CPU / 512 MiB；客户端是独立容器，1 CPU / 256 MiB、16 个连接、2 个 pgbench 线程。
- 保持 fsync=on、synchronous_commit=on；prepared 协议、TCP loopback；未测 Rust/Tower/HTTP 及连接池排队。
- 四种组合分别为精确过期时间/取整到秒 × fillfactor=100/80。只改变清理用 expires_at；tat_us、配额与 retry/reset 计算保持微秒精度。
- 取整使用整数商和余数，避免 BIGINT 加法溢出；始终保证 TAT ≤ expires_at < TAT＋1 秒。
- 每组每轮先重新建立相同数量的活跃状态行，再执行固定 1,024 次预热；普通场景测量 100,000 次调用，热点场景测量 4,096 次，各重复 3 轮。
- 所有负载使用 1 微秒补充间隔、总突发容量 10,000,000，确保每次都放行并更新，集中比较写入路径。
- 四张**试验表统一关闭自动 vacuum**，排除清理时机对固定工作量膨胀比较的干扰；每轮采集 seeded/before/after/vacuumed 四份快照，负载后单独执行普通 VACUUM ANALYZE。
- HOT 来自 n_tup_hot_upd/n_tup_upd 的测量区间增量；计数刷新后校验更新数等于固定调用数。WAL 使用负载前后 WAL insert LSN 差值，不包含后续采样和手动 vacuum。
- 使用 pgstattuple 取得实际 live/dead tuple、空闲空间，pgstatindex 取得两个 B-tree 的页数和叶页密度；同时保存关系大小和 n_dead_tup 估计值。
- 逐调用日志完整记录，没有抽样。所有表大小均含相同固定预热量；百分比与吞吐取各版本三轮中位数。

## fillfactor 的额外代价与收益

1,000 个 key 的初始 heap：fillfactor=100 为 64 KiB，80 为 80 KiB。10,000 个 key：592 KiB 与 744 KiB。预留空间使初始 heap 增加约 25%，但不是预先分配额外业务行。
相对于仅取整，组合方案在 1,000 个 key 下额外减少约 3.1% WAL，在 10,000 个 key 下额外减少约 9.2%；热点 key 基本没有额外 WAL 收益。不能因为某组吞吐更高，就认定 80 是所有部署的最佳默认值。

## 限制

这是关闭试验表自动 vacuum 的固定工作量实验，适合比较更新机制和清理前空间增长；不是启用真实自动维护后的长期稳态测试。
所有请求都放行，尚未测新 key 持续涌入、大量拒绝、业务查询混部或真实网络。Docker CPU 为限额而非独占 CPU，宿主机上其他容器仍在运行，吞吐存在波动。
取整只延后清理不到一秒，不降低限流计时精度；实际落地仍应保留这一不提前删除状态的约束。
试验 SQL 为对照包含 autovacuum_enabled=false，**不能直接作为生产迁移使用**。
